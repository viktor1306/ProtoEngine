## Правило завершення

Перші вікно, модель або тінь є проміжними результатами. v0.1 завершується
лише після повного погодженого циклу й звіту про масштабування. Точкові лампи
з динамічними тінями обов'язкові до приймання v0.1.

Етапи мають окремі перевірки й придатний до запуску результат. Нову оптимізацію
порівнюємо з попереднім працездатним станом за однакової сцени/якості; результати
не підмінюються вимірюванням простішого зображення.

## M0 — збірка, залежності й вікно Vulkan

**Завершено 2026-09-08.** CTest: 2/2 Debug, 2/2 Release. Core + synchronization
validation у Debug: 0 errors, 0 warnings; raster/readback і native lifecycle пройшли.

Результат:

- Кореневий CMake-проєкт, pinned dependencies, Debug/Release presets, CTest.
- Нативне вікно GLFW, Vulkan 1.3 device/swapchain, resize/minimize/close.
- ImGui Vulkan backend, docking layout, українські символи, DPI, clipboard.
- Кольоровий трикутник і readback перевірочного кадру; правильні winding/Y/depth.
- Shader compiler у локальному tools-кеші; Python/повний SDK не встановлюються.
- Перевірка runtime-передумов shader compiler до збірки, включно з його MSVC DLL.
- Validation layers тільки в процесах Debug; основа журналу й CPU/GPU markers.

Критерій переходу: чиста збірка на наявному GCC; коректне закриття й повторне
відкриття вікна; відсутність validation errors у базовому сценарії. GLFW,
ImGui backend і surface мають працювати разом, а не лише компілюватися окремо.

Діагностичні probes, виконані під час проєктування, покрили лише частину
сумісності бібліотек і compute-пристрою. Вони не закривають M0.

## M1 — сцена та надійне збереження

**Завершено 2026-09-08.** 20 перевірок контракту сцени; CTest 5/5 у Debug
та 5/5 у Release разом із регресійними перевірками M0. Native UI перевіряє
вибір куба, перетягування координати з одним Undo та save/reopen. Debug
core + synchronization validation: 0 errors, 0 warnings.

Результат:

- EntityId/AssetId/runtime handles, щільні component pools, parent/children.
- Transform dirty propagation, bounds, camera та об'єктні properties.
- Завантаження/збереження versioned JSON, validation до публікації стану.
- Атомарна заміна одного файла зі збереженням попередньої версії.
- Базові редакторські команди та selection; куб/площина для локальної перевірки.

Перевірки: save/load ієрархії; parent rotation/non-uniform/negative scale;
відхилення циклу; невідомі/дубльовані ID; пошкоджений документ; stale handle;
видалення піддерева й Undo; збереження dirty-стану після невдалого запису.

## M2 — імпорт, ресурси та матеріали

Реалізовано. Debug і Release: 8/8 CTest; 17 контрактних тестів ресурсів,
20 тестів сцени, GPU-перевірки glTF і GLB. [Докази та обмеження](M2_REPORT.md).

Результат:

- glTF/GLB → підресурси зі сталими UUID, `.meta`, відновлюваний registry.
- PNG/JPEG, залежності URI, buffer views, normal/tangent та material slots.
- Підготовлений cache, worker jobs, черга GPU-upload із бюджетом за кадр.
- PBR opaque/mask, double-sided, inspector матеріалу, ієрархія імпортованої моделі.

Перевірки: одна модель у кількох instances ділить геометрію; зовнішній `.bin`
і texture не губляться при імпорті; embedded texture із GLB; відсутні/пошкоджені
залежності; непідтримане required extension; normal map і negative scale;
відсутність подвійного декодування тих самих даних при кожному кадрі.

Ресурси для перевірок мають зафіксовані SHA-256, джерело й ліцензію.
Тестові альфа-маски та примітиви можна створювати детерміновано власними засобами.

## M3 — динамічне освітлення й тіні

**Завершено 2026-09-08.** CTest: 12/12 Debug і Release. 18 сценаріїв,
84 кадри, 13 438 RGB/depth проб, 31 повне порівняння зображень.
[Докази, запуск і межі перевірки](M3_REPORT.md).

Результат:

- Напрямлене сонце з cascaded shadow maps.
- Точкові лампи з cube shadow maps, alpha-aware shadow pass.
- Видимість, bounds, batching/instancing; reference lighting path для порівнянь.
- GPU-списки світла для плиток, overflow без мовчазного обрізання світла.
- Dirty shadow cache та робота пакетами при обмеженій пам'яті pool.

Обов'язкові сценові перевірки:

1. Лампа обходить нерухому модель; напрям і форма тіні змінюються.
2. Модель рухається біля нерухомої лампи; затінення навколишніх поверхонь змінюється.
3. Лампа й модель є нащадками рухомих/обертових батьків.
4. Листя/сітка з `MASK` відкидає тінь із вирізами від обох типів світла.
5. Caster поза кадром відкидає тінь на видиму частину сцени.
6. Зміна геометрії, радіуса лампи або маски інвалідує потрібні карти.
7. Зміна лише кольору/яскравості не спричиняє зайвого depth-pass.
8. Один lighting-пакет і кілька пакетів дають еквівалентне освітлення в межах
   погодженої похибки накопичення floating-point.
9. Кешований і примусово оновлюваний режими не розходяться під час руху.

Окрім image comparisons, потрібен перегляд тіней у русі: мерехтіння, відрив
тіні, self-shadowing, seams і межі каскадів не оцінюються лише одним кадром.
Показники shadow passes/cache hits фіксуються, щоб коректність кешу не була
єдиним результатом його перевірки.

## M4 — повний редактор і файловий Undo/Redo

**Реалізовано 2026-09-08.** CTest: 19/19 Debug і Release, включно з M0–M3.
Окремо перевірене відкриття без кешу `.proto` та повторений нативний проєктний
сценарій після цієї зміни. [Докази й межі](M4_REPORT.md).

Результат:

- Чотири погоджені області редактора, дерево, inspector, маніпулятори.
- Drag gesture = одна команда; історія поточної сесії з обліком пам'яті.
- Файлова навігація, move/rename/copy/paste, видимі конфлікти імен.
- Транзакційне перенесення `.meta`, коригування URI та збереження UUID.
- Журнал відновлення незавершених багатофайлових операцій.

Перевірки: move/rename/copy → Undo → Redo → save → reopen; копія групи з
внутрішніми/зовнішніми залежностями; нові ID копії й сталі ID при Redo;
зовнішня зміна файла перед Undo; аварійне припинення операції між кроками;
шляхи з пробілами й українськими символами; спроба виходу за project root.

виправлень повторено по 3/3 змінених сценарії у двох конфігураціях.
Нативний Play перевіряє власну C++-збірку, рух, тіні, помилки, Stop і збереження

Результат:

- Збірка Player конкретного проєкту; помилки з файлами/рядками в журналі.

- Play snapshot + pinned resource manifest, окремий процес/вікно, Stop.

## M6 — збирання самостійної програми

**Завершено 2026-09-09.** Повний CTest M0–M6: 30/30 Debug та 30/30 Release.
Самостійний приклад перенесено й запущено з іншої робочої папки без шляхів
компілятора; F1 Apply/Cancel, чотири збої та відновлення, persistence,

Результат:

- Пакування startup scene, dependency closure і additionalAssets.
- `.exe`, підготовлені blobs, SPIR-V, graphics config, notices і потрібні DLL.
- Перевірка пакета перед публікацією output-папки, збереження попередньої збірки.
- Невелика панель графічних налаштувань у Player.

Перевірки: запуск із іншого working directory; із скопійованої папки;
без шляхів до компілятора/редактора/авторського проєкту; missing resource;
правильне включення additionalAssets; розбір імпортованих DLL executable.
Чисте інше Windows-середовище є окремою перевіркою. Якщо його немає, звіт
прямо обмежує висновок локальними тестами, без заяви про перевірку на іншому ПК.

## M7 — масштабування та усунення виміряних вузьких місць

Засоби економії ресурсів вводяться в попередніх етапах. Тут перевіряється їх
сукупна поведінка й усуваються виміряні обмеження, з before/after-порівняннями.

### Набір навантажень

| Сцена | Призначення |
| --- | --- |
| Empty | Окремо idle/interactive Editor і порожній Player: CPU, GPU, пам'ять. |
| Small | Повний демонстраційний склад: PBR, MASK, ієрархія, сонце й кілька ламп. |
| Instances-1000 | 1 000 повторів однакової геометрії: sharing, batching, transforms. |
| Instances-10000 | 10 000 повторів; окремо переважно видимий і переважно невидимий набір. |
| Lights | Незмінна геометрія та 1/8/32/128 ламп, що впливають на тестову область. |
| Moving-shadows | Статичні та рухомі лампи/casters, у тому числі переповнення pool. |
| Asset-cycle | Повторні load/unload та файловий Undo/Redo з перевіркою власників ресурсів. |

Це заплановані навантаження, не обіцянка певного FPS або остаточні ліміти.
Геометрія, матеріали, видимість, camera path і джерела фіксуються в benchmark
manifest; звіт показує фактичні counts, а не лише назву сцени.

### Умови вимірювання

- Release з однаковими прапорами, shader binaries і content hashes.
- Фіксовані resolution/render scale, camera path, profile та shadow parameters.
- VSync вимкнено для throughput-тесту; frame pacing оцінюється окремо з VSync.
- Validation вимкнено для швидкодії; перевірка коректності виконується з validation.
- Warm-up, щонайменше три повтори, однакова тривалість; порівняння median/p95/p99.
- Живлення й фонове навантаження записуються; системні power/driver-політики
  не змінюються приховано заради кращого результату.
- Cold/warm load розрізняються за точною процедурою. Очищення лише власного
  кешу не називається очищенням дискового кешу Windows.

### Метрики

CPU frame time окремо від GPU timestamp time; draw/dispatch counts; видимі
instances й лампи; shadow passes/cache hits; upload bytes; working set/private
bytes; облік виділених GPU-ресурсів і дані VMA budget за наявності; load time.
Оцінена GPU-пам'ять не видається за точний фізичний обсяг VRAM.

Дані пишуться в JSON/CSV разом із manifest. Для оптимізації потрібні одночасно
еквівалентний результат зображення та виміряна зміна витрат. Відсутність виграшу
також фіксується; складніша реалізація не залишається лише через її назву.

## Подальші рішення за результатами роботи

M0 може виявити потребу в іншому сумісному revision окремої залежності — він
оновлюється разом із перевіркою та lock. M3/M7 уточнюють shadow budgets,
кількість workers і пакети команд за фактичним результатом. Ці уточнення
не скасовують погоджену функціональність або не додають ray tracing, фізику,
скелетну анімацію чи BLEND до v0.1.
