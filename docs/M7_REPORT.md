# M7 — масштабування та виміряна оптимізація

Дата: 2026-09-09. M7 реалізовано; фінальні Debug та Release пройшли 41/41
перевірку, дев'ять контрольних зображень збіглися побайтово. Є виміряні
зменшення часу окремих етапів підготовки CPU. Загальне прискорення GPU/FPS
не встановлено: варіативність велика, а частина сцен має гірші результати.

## Що змінилося

Додано детерміновані native benchmark-сцени, вимірювання редактора,
цикли ресурсів і файлових операцій, JSON/CSV та відтворювані PowerShell-скрипти.
GPU timestamp-вибірки мають окремі serial і перевірку повного діапазону;
прогрівання та контрольні кадри виключені з часової вибірки.

Початкова матриця показала витрати CPU на підготовку поверхонь і планування
тіней для 10 000 об'єктів. За її результатами:

- площини відсікання камери, каскадів і граней тіней готуються один раз;
- межі casters у координатах сонця обчислюються один раз для всіх каскадів;
- спільний матеріал розв'язується один раз на кадр;
- таблиця пошуку instances заздалегідь резервує потрібну місткість.

Новий кеш матеріалів живе лише протягом одного gather. Міжкадрове володіння
ресурсами не розширено. Шейдери, якість, геометрія й правила світла не змінені.

Перевірено й відхилено окремий кеш меж та mesh ID кожного instance. У прямому
порівнянні V1/V2 його видалення дало приблизно +0,6% часу кадру для 10k moving
і −1,0% для moving lights 32 — корисного прискорення від кешу не встановлено.
Приватна пам'ять процесу в першій сцені зменшилася приблизно на 0,55 MiB за
медіанами виміряних максимумів; це не точний облік окремого allocation.
У фінальному V2 цей кеш відсутній. [Дані видалення кешу](research/m7/ablation/summary.json),
незмінний V1 збережений у `.cache/m7-candidate-v1`.

Повна перевірка також виявила стару помилку службового Player: виняток під
час `--describe-behaviors` відкривав діалог і затримував повернення помилки
до таймауту. Додано виключення для цього службового режиму. Помилки звичайного
інтерактивного запуску й далі показують діалог. Наявний M5-тест перевіряє
виняток і справжнє зависання окремо; його умови не послаблено.

## Умови й відтворення

ПК: Core Ultra 7 255H, 16 логічних процесорів, 68 111 511 552 байти RAM,
Intel Arc 140T, драйвер 32.0.101.8508. Windows balanced power plan, живлення
від мережі. Стан записаний у `research/m7/initial/environment.json` і host-файлах
кожного запуску. Налаштування ОС/драйвера та інші програми не змінювалися.

Release: GCC 16.2.0, `-O3 -DNDEBUG`; Vulkan 1.3. Основний target 1280×720,
scale 1; маленьке вікно показу 320×180, VSync off, validation off. Є справжні
команди renderer і PlayerPresenter та Win32 presentation. Це вимірювання
runtime render path; воно не включає довільний C++-код користувацького проєкту
й не дорівнює FPS повноекранної готової гри.

Before runtime — незмінні алгоритми M6 з перевіреним вимірювачем M7:
`.cache/m7-instrumented-baseline`. Для Editor використано свіжу незалежну
збірку `build/m7-editor-reference` із джерел `.cache/m7-editor-reference-source`;
лог підтверджує компіляцію всіх залежних об'єктів. Її результати —
[editor-reference](research/m7/editor-reference/index.json).
Попередню спробу Editor baseline виключено через збережені інкрементально
об'єктні файли: [пояснення](research/m7/editor-baseline/PROVENANCE-NOTE.md).
After — `build/m7-release`. Оригінальні M6 executable та SDK не перебудовувались.

Основна матриця містить 14 сцен × 3 повтори, 2 с прогрівання + 5 с вибірки.
Фінальна before/after-серія чергує порядок збірок між повторами. GPU-прогони
послідовні; паралельних компіляцій та інших прогонів рушія немає. Власні
тимчасові ресурси відокремлені від користувацьких проєктів.

Підсумкові median/p95/p99 — медіани відповідних статистик окремих повторів,
а не перцентилі об'єднаної вибірки. Діапазони між повторами збережено.
`wall_ms` містить очікування; він не називається активним CPU time.
Час GPU і CPU не з'єднується за позицією рядка. Throughput використовує
фактичну тривалість, включно з накладними витратами вимірювача.

Повні дані фінального V2: [JSON-підсумок](research/m7/final/summary.json),
[усі запуски CSV](research/m7/final/summary-runs.csv),
[групи й перцентилі CSV](research/m7/final/summary-groups.csv),
[порівняння CSV](research/m7/final/summary-comparison.csv).
У кожній сцені збігаються content/shader hashes; усі 84 запуски мають повну
відокремлену GPU-вибірку та exit code 0. Логи й raw JSON/CSV збережені.

Додаткові серії збережено окремо: [перший V1](research/m7/paired/summary.json),
[його повтор](research/m7/recheck/summary.json),
[контроль тим самим executable](research/m7/identical-control/summary.json).
У контролі з однаковим шляхом і SHA-256 медіани GPU окремих запусків
коливалися від 27,09 до 59,29 мс. Це показує нестабільність умов; не доводить
ані відсутності регресії, ані її причини. Погіршення V1 для moving lights 32
не повторилось у фінальному V2 за груповою медіаною, але інші сцени V2 стали
повільнішими. Нижче наведено всі результати, без вибору лише кращих.

## Asset lifecycle

У кожній серії було 3 asset-запуски по 12 циклів. Перевірки weak owners, hash/ID restoration і cleanup пройшли для кожного циклу; candidate і reference використовують той самий `ProtoAssetBenchmark.exe`, SHA-256 `7284cc2b0c7f3d5f50ea324670222058c7de040a2f05d7d41a1076851894cff9`.

| Серія | Initial import | Cooked cold | Warm load | Material/document load-unload | private / working peak, B |
|---|---:|---:|---:|---:|---:|
| reference | 95.134 | 83.558 | 28.980 | 259.197 | 20750336 / 26726400 |
| final | 105.907 | 86.719 | 27.183 | 251.527 | 21610496 / 26894336 |

Медіани послідовності move (redo/undo/redo-again/final-undo): `93.056/89.867/90.153/90.799 → 109.649/115.320/114.229/116.241` мс; copy: `68.531/62.819/67.593/59.552 → 88.439/79.163/85.222/75.233` мс. GPU-тест пройшов 12/12 циклів із 0 помилок validation: VMA після unload залишалася **50,461,696 B**, а максимум після load — **50,505,728 B**.

Ці результати є описом конкретних запусків, а не універсальним FPS чи висновком про відсутність регресії. p99 для запусків із <1000 кадрів має мало спостережень; ліміт спільних ресурсів інтегрованої GPU не є фізичною VRAM.

Основний профіль: сонце 1024, 3 каскади, PCF 3×3; точкові тіні 256,
9 taps, pool 48 MiB; view distance 500. Для великого набору дальність сонця
350, для малих сцен 60. Повні параметри й content hashes є в manifests.
Процедурні ресурси оригінальні; це тест спільної простої геометрії,
не 10 000 незалежних складних моделей із різними текстурами.

## Перевірки та рішення

- Фінальний V2: **41/41 Release, 156,99 с**; **41/41 Debug, 207,43 с**.
  [Release XML](research/m7-v2-release.xml), [Debug XML](research/m7-v2-debug.xml).
- **9/9 контрольних PNG** до/після збігаються побайтово; candidate запускався
  з Vulkan validation. [Порівняння](research/m7/captures-final/comparison.json).
- GPU load/unload: по 12 циклів у кожній конфігурації, жодної помилки
  validation, власники ресурсів звільняються, VMA стабілізується.
- CPU assets: 6 запусків по 12 циклів одним незмінним executable. UUID,
  вміст, Undo/Redo, weak owners і очищення перевірено; різниця часу між цими
  серіями не є доказом оптимізації assets.
- Незалежний Astra/max перегляд перевірив зміни, виправлення вимірювачів,
  усі 84 фінальні runtime-запуски, походження збірок, лічильники та висновки.
  Зауваження до коректності усунені; обмеження продуктивності наведено явно.

Залишено прості зміни, які усувають повторні підготовчі обчислення CPU;
додатковий кеш меж видалено після прямого порівняння. Загальний FPS/GPU
не оголошується кращим. Наприклад, у фінальній серії small мав +14,3% wall,
lights-1 +63,7%, lights-32 +23,0%; ці погіршення не приховуються.
Зменшення wall для 10k moving на 24,6% належить саме цій нестабільній серії
і не переноситься на інші сцени або ПК як оцінка прискорення.

## Межі висновків

Багато точкових ламп із динамічними тінями залишаються дорогим GPU-навантаженням.
Переповнений пул потребує повторних shadow passes і lighting batches;
економія пам'яті має вимірювану ціну. CPU-оптимізація не означає однакового
прискорення GPU-bound сцен. Короткі дорогі прогони дають мало спостережень p99.

Cold asset load означає видалення лише власного cooked cache. Дисковий кеш
Windows не очищувався. Working set/private bytes і VMA allocations мають
різні значення; heap budget інтегрованої GPU не є фізичною VRAM. Пули та
місткості буферів можуть залишатися після unload — перевіряється відсутність
росту й звільнення власників ресурсів, а не повернення до холодного старту.

Один проміжний Release-прогін отримав помилку Windows при перейменуванні
тимчасового каталогу нового M4-проєкту. Код помилки тоді не записувався;
причину не встановлено. Додано точний GetLastError і захист тесту від
подальшого доступу до нествореної сесії. Після цього 20 Release і 10 Debug
повторів пройшли. Це не доводить причину одиничного файлового збою.

Усі висновки стосуються цього ПК й наведених умов. M8 — окреме наскрізне
приймання v0.1 — цим етапом не виконується.
